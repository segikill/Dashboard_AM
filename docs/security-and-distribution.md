# Защита доступа и распространение атласа

Дата решения: 22.10.2026. Относится к выпуску `v2.0.0`.

## Текущее состояние

Сайт опубликован как статический GitHub Pages. Браузер получает HTML, JavaScript, карты и файлы данных, поэтому любой посетитель опубликованного сайта может скачать их через обычные средства браузера. В текущем выпуске нет формы входа и это корректно: локальный пароль в HTML/JavaScript не дал бы защиты.

В приложении нет серверной базы данных или SQL-запросов. Поэтому SQL-инъекция не является применимой атакой к текущей архитектуре. Она появится как риск только при добавлении серверного API и БД; тогда параметры запросов должны передаваться через параметризованные запросы, а не составляться из пользовательского ввода.

## Почему пароль в статическом сайте не решает задачу

Нельзя одновременно выполнить следующие условия только средствами GitHub Pages или ZIP-архива:

1. пароль не хранится у пользователя;
2. браузер проверяет пароль без сервера;
3. данные не скачиваются до проверки пароля.

Для проверки пароля браузеру нужен алгоритм и проверочные данные. Любой секрет, хеш или ключ, включённый в статический сайт, можно извлечь; даже после «входа» файлы данных остаются доступными по прямым URL. Такая форма является лишь визуальным экраном, а не контролем доступа. Её не следует добавлять.

GitHub Pages также не подходит для чувствительных данных в обычной конфигурации: публичные Pages доступны в интернете. Приватная публикация с контролем доступа GitHub Pages требует GitHub Enterprise Cloud и организационного репозитория. См. официальные документы GitHub: [видимость Pages](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site) и [публикация Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## Подходы, которые действительно защищают данные

| Сценарий | Решение | Что защищает | Ограничение |
|---|---|---|---|
| Публичная демонстрация | Оставить GitHub Pages публичным и публиковать только допустимые обезличенные данные | Ничего от посетителя; это прозрачная публичная публикация | Не подходит для ограниченных данных |
| Доступ для конкретных сотрудников через браузер | Перенести опубликованную сборку за шлюз идентификации: например, Cloudflare Access перед Worker/Pages либо другой корпоративный SSO-шлюз | Каждый HTTP-запрос проверяется до выдачи файлов; пароля нет в коде сайта | Нужны отдельная учётная/identity-система и настройка домена/шлюза; GitHub Pages на `github.io` сам по себе так не защищается |
| Передача автономного выпуска | Передавать зашифрованный архив 7z/ZIP с AES-256, включить шифрование имён файлов; пароль передать другим каналом | Файлы до распаковки | Получатель после распаковки имеет копию данных и может её переслать |
| Полный контроль и журналирование | Серверное приложение с индивидуальными учётными записями, HTTPS, ограничением попыток, журналом и отзывом доступа | Доступ к данным и управление пользователями | Нужен сервер/облачная среда и сопровождение |

Cloudflare Access работает до выдачи защищаемого приложения: он проверяет, авторизован ли пользователь, и показывает вход либо блокирует запрос. Официальное описание: [Cloudflare Access для Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/). Это не «пароль в коде сайта» и может продолжать собирать сайт из Git, но перед настройкой нужно отдельно подтвердить тариф, домен и допустимый способ идентификации.

## Рекомендация для этого проекта

1. Пока данные предназначены для публичной демонстрации — оставить GitHub Pages без экрана пароля и публиковать только обезличенный набор.
2. Для передачи заказчику — подготовить отдельный офлайн-пакет: `site/` с текущей сборкой, `README` с инструкцией запуска, контрольная сумма SHA-256 и зашифрованный архив. Пароль передавать отдельным каналом. Это защищает доставку, но не ограничивает законного получателя после распаковки.
3. Если требуется ограничить именно просмотр в браузере — сначала выбрать владельца доступа (список e-mail или корпоративный SSO), затем развернуть сайт за Cloudflare Access/другим gateway. Только после этого можно добавить экран входа, который будет выдавать провайдер идентификации, а не JavaScript сайта.

## Запреты для следующего этапа

- Не хранить пароль, API-ключ или хеш пароля в репозитории, GitHub Pages, `dist/` или ZIP-архиве рядом с незашифрованными данными.
- Не добавлять клиентскую форму «входа» как средство защиты данных.
- Не публиковать персональные или ограниченные исходные записи на публичном Pages.
- При появлении серверного API использовать индивидуальные учётные записи, Argon2id для хранения паролей, параметризованные запросы, rate limit, HTTPS и серверную проверку прав до выдачи данных.
